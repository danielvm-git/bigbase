# BUG-2026-06-01T193841: GitHub and Sites components not wired into backend, proxy, or dashboard UI

## Problem

The `github` and `sites` components are fully implemented (Go backend components with tests, React UI pages), but:

1. **Backend (Go)**: `main.go` does not import, instantiate, or `k.Register()` the `github` or `sites` components. They are dead code at runtime.
2. **Proxy routes**: No `p.Handle(...)` calls for `/api/github/*` or `/api/sites/*` endpoints.
3. **Frontend (React)**: No routes in `App.tsx` for `/deploy/new` (CreateSitePage) or `/deploy/:siteId` (SiteDetailPage). The existing pages exist but are dead code.

**Actual behavior**: Running `bigbase serve` — the GitHub and Sites components are not registered. The dashboard has a "Deploy" sidebar item but clicking it shows the legacy DeployPage (deployments list), not the Sites wizard experience. The `/deploy/new` and `/deploy/:siteId` routes return 404. The existing frontend pages (`CreateSitePage.tsx`, `SiteDetailPage.tsx`) are never imported in `App.tsx`.

**Expected behavior**: 
- `go run . components list` shows both `github` and `sites` components
- API endpoints `/api/github/*` and `/api/sites/*` are reachable
- `#/deploy/new` loads the CreateSitePage wizard
- `#/deploy/:siteId` loads the SiteDetailPage
- The existing `/deploy` sidebar entry serves as the Sites entry point

## Root Cause Analysis

The bug has three independent layers that all need fixing. None individually is sufficient.

### Layer 1 — Backend registration (Go)

**File**: `main.go` (lines 14-28 imports, lines 94-150 instantiation/registration)

`main.go` imports 14 components. `github` and `sites` are not among them. They are not instantiated with their constructors, not passed to `k.Register()`, and consequently the kernel has no knowledge of them.

The `github` component:
- Package: `github.com/danielvm/bigbase/components/github`
- Constructor: `github.New(github.Options{DB: d, Logger: logger})`
- Optional fields: `GitDir`, `AppID`, `AppSlug`, `PrivateKeyPath`, `WebhookSecret`
- Name(): returns "github"

The `sites` component:
- Package: `github.com/danielvm/bigbase/components/sites`
- Constructor: `sites.New(sites.Options{DB: d, Logger: logger})`
- Optional: `TriggerDeploy` function
- Name(): returns "sites"

### Layer 2 — Proxy route wiring

**File**: `main.go` (lines 152-183)

The handler for each component is wrapped with middleware (auth + monitoring) and registered against the proxy. No such wiring exists for `github` or `sites`.

Required proxy routes:
```
p.Handle("/api/github/", ...)  — from github.Handler() (status, install, callback, repos, webhook)
p.Handle("/api/sites", ...)    — from sites.Handler() (list + create)
p.Handle("/api/sites/", ...)   — from sites.Handler() (get by ID, redeploy)
```

### Layer 3 — Frontend UI (React)

**File**: `ui/src/App.tsx` — no import or routes for `/deploy/new` → CreateSitePage or `/deploy/:siteId` → SiteDetailPage. The spec defines these routes under `/deploy` (not `/sites`), enhancing the existing Deploy section rather than adding a separate one.
**File**: `ui/src/Layout.tsx` — the "Deploy" sidebar item already exists pointing to `/deploy`. No new sidebar items needed — the existing Deploy entry becomes the Sites entry point.
**File**: `main.go` (line 185) — `spaPaths` already includes `/deploy` but not `/deploy/new` (needed for direct URL access).

The existing pages `CreateSitePage.tsx` and `SiteDetailPage.tsx` exist but are never imported in `App.tsx`.

### Risk level: Medium

The components themselves are well-implemented and tested. The missing wiring is additive — adding imports, registration calls, routes, and UI entries. There is a low risk of breaking existing functionality.

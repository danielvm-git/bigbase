## Vulnerability Assessment

### 1. SQL Injection (CWE-89) — SQL-Safety Doctrine Proven

**Threat:** User-controlled input reaching SQL query construction via string
interpolation.

**Analysis:** Every SQL query across all deploy-component files uses `?`
parameter binding with `ExecContext` or `QueryRowContext`:

```
gateway.go          → INSERT INTO deployments (?, ?, ?, ...)
engine.go:28        → SELECT name FROM git_repos WHERE id = ?
engine.go:67        → INSERT INTO deployments (id, repo_id, ...) VALUES (?, ?, ...)
engine.go:110       → SELECT pid FROM deployments WHERE id = ?
engine.go:122       → UPDATE deployments SET status = ? WHERE id = ?
engine.go:293       → UPDATE deployments SET error_message = ? WHERE id = ?
orchestrator.go     → All queries parameterized (verified)
manifest.go         → All queries parameterized (verified)
logs.go             → All queries parameterized (verified)
state_transitions.go → All queries parameterized (verified)
```

No `fmt.Sprintf` or string concatenation is used in any SQL context.

**False-positive guard:** Not a false positive — this is the affirmative proof
of the SQL-safety doctrine (e45s41). All parameterized, all safe.

**Verdict:** PASS. SQL-safety doctrine PROVEN across all deploy-component files.
Confidence: 10/10.

### 2. Command Injection (CWE-78) — Git Checkout via User-Controlled Branch

**Threat:** User supplies a `branch` value in the deploy API request
(`POST /api/deploy`) that gets passed to `git checkout`. If shell-invoked,
`"; rm -rf /"` could execute arbitrary commands.

**Analysis:** Trace:
1. `HandleCreate` (gateway.go:31-50) reads `req.Branch` from JSON body
2. Passed to `d.Trigger()` (engine.go:19) as `branch` param
3. `Trigger` stores in DB via parameterized query (engine.go:67)
4. `cloneAndCheckout` (engine.go:306) passes to `exec.CommandContext(ctx, "git", "checkout", branch)`

Go's `exec.Command` does NOT invoke a shell. The `branch` value becomes a single
argv element in the `git` process. Even `"; rm -rf /"` would be treated by git
as a branch name argument, not executed as a shell command.

Additionally, `repoID` (used to construct `filepath.Join(d.gitDir, repoID+".git")`)
is server-generated by `kernel.GenerateID()` as a 32-character hex string
(rand.Read → hex.EncodeToString, utilities.go:19-25). Never user-controlled,
cannot contain `/` or `.` traversal sequences.

**False-positive guard:** Go's `exec.Command` with argv form is explicitly the
safe pattern per REFERENCE-vuln-categories.md. The `shell=True` / `os.system`
pattern would be dangerous; this is not that pattern.

**Verdict:** PASS. No shell injection vector. Confidence: 10/10.

### 3. Server-Side Request Forgery / Path Traversal (CWE-22, CWE-918)

**Threat:** Attacker provides a malicious `repo_id` containing `../` to escape
the git directory and clone from an arbitrary filesystem path.

**Analysis:** The repo lookup at engine.go:28 does:
```go
d.db.QueryRowContext(ctx, "SELECT name FROM git_repos WHERE id = ?", repoID)
```
If the repo exists in the database (i.e., was previously created via the git
component), `repoID` is a value stored during repo creation — which itself uses
`kernel.GenerateID()` (32-char hex). Line 138: `repoPath := filepath.Join(d.gitDir,
deploy.RepoID+".git")` — `deploy.RepoID` comes from the DB row, not the request.

If the repo does NOT exist, `Trigger` returns `ErrRepoNotFound` at line 30.

**Path traversal guard (manifest.go:108-129):** The `LoadManifestPath` function
applies `filepath.Clean` + `filepath.IsAbs` + `strings.HasPrefix` to prevent
`../` escape. Documented as CWE-22 fix in previous review.

**Verdict:** PASS. No path traversal vector. Confidence: 10/10.

### 4. Authentication/Authorization Bypass — Missing Auth on Build Logs Endpoint

**Threat:** The `handleDeployLogs` endpoint could expose build output (which may
contain environment variables, source code snippets, or internal paths) to
unauthenticated callers.

**Analysis:** Audit of gateway.go route registration and middleware chain:

```
HandleCreate   → Requires site key (gateway.go:52-59: SiteIDFromContext check)
HandleList     → Requires auth (standard middleware)
handleDeployLogs → Protected by auth middleware (same router, no skip registration)
```

All deploy endpoints share the same router group and enforcement layer.
Centralized auth gate: `r.Use(authMiddleware)` pattern confirmed.

**Verdict:** PASS. Auth gate consistent across all deploy endpoints.
Confidence: 9/10.

### 5. Insecure Direct Object Reference (CWE-639)

**Threat:** User can access another user's deployment logs or status by
guessing/fuzzing deployment IDs.

**Analysis:** Deployment IDs are generated by `kernel.GenerateID()` (32-char hex
from 16 bytes of crypto/rand). This is UUID-quality randomness:
- 128 bits of entropy (rand.Read from crypto/rand)
- 2^128 possible values
- Unguessable per Precedent Rule 2 (UUIDs are unguessable — no validation needed)

Additionally, site-key scoping applies: `SiteIDFromContext(r.Context())` enforces
that a deploy key can only access deployments belonging to its authorized site.

**Verdict:** PASS. Unguessable IDs + site-key scoping prevent IDOR.
Confidence: 10/10.

### 6. Deploy Log Map Eviction (logs.go:8-28)

**Threat:** Log entries may be evicted non-deterministically because Go map
iteration is randomized, potentially causing older deployment logs to survive
while newer ones are evicted.

**Analysis:** The eviction logic in `initDeployLogs` uses Go's random map
iteration to select a victim when the capacity (`maxDeployLogDeployments = 100`)
is reached:

```go
for len(d.deployLogs) >= maxDeployLogDeployments {
    var victim string
    for k := range d.deployLogs {
        if k != id {
            victim = k
            break
        }
    }
    if victim == "" {
        break
    }
    d.deleteDeployLogs(victim)
}
```

This means:
- The first key encountered by the map iterator (other than the new one) is evicted
- Map iteration order is randomized per Go spec, so eviction is non-deterministic
- Not a bug per se, but unpredictable — the same deployment could survive or be
  evicted depending on map hash state

**False-positive guard:** Build log data only. No credentials, no PII, no
operational state. This is a quality/observability issue, not a security vuln.

**Verdict:** NOT a security finding. Non-deterministic eviction could cause
surprising log loss in edge cases. Recommend deterministic FIFO eviction or
TTL-based retention. Confidence (security): 1/10. Suppressed per FP rule #4
and #10 (Resource management, Precedent).

### 7. Manifest Start.Command Execution (engine.go:431)

**Threat:** The user's deployment manifest specifies a Start.Command that gets
executed as a subprocess. If the manifest is attacker-controlled, arbitrary
commands could run.

**Analysis:** The manifest comes from the user's own deployed repository. The
entire purpose of BigBase's deploy component is to build and run user code from
git repos. By design:
- User pushes their code → BigBase builds it → BigBase runs it
- The `Start.Command` is parsed with `strings.Fields()` and passed to
  `exec.CommandContext` as argv (no shell)
- Process is managed by a Supervisor that enforces restart limits

**False-positive guard:** The product's purpose is to run user-provided code.
This is by design, not a vulnerability. Per Precedent reasoning: "If the
product's purpose is to run user code, that's not a vuln."

**Verdict:** NOT a security finding. By design. Confidence: 1/10. Suppressed.

## Verdict

**PASS.** All security patterns are correctly applied across the deploy component.
No vulnerabilities were found at confidence ≥ 8.

The following secure patterns are confirmed:
- **SQL-safety doctrine (e45s41): PROVEN** — every query in the deploy component
  uses `?` parameter binding; zero instances of string interpolation in SQL
- **No-shell subprocess pattern** — all `exec.Command` calls use argv form;
  zero instances of `shell=True` or `os.system` equivalents
- **Auth gate consistency** — all deploy endpoints gated by same middleware
- **Unguessable IDs** — `kernel.GenerateID()` from `crypto/rand`; 128 bits
- **Path traversal hardening** — `filepath.Clean` + prefix check (manifest.go)

## Recommended Non-Security Fix

**Deploy log eviction (logs.go:8-28):** The `initDeployLogs` eviction uses Go's
randomized map iteration for victim selection, making log retention
non-deterministic. Recommended fix: use a deterministic FIFO queue or
insertion-order tracking so the oldest deployment logs are evicted first.
This is a log-line retention issue, not a security vulnerability.

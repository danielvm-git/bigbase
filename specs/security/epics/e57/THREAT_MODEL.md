## Change Analysis

### Change 1: Hoist Logger/DBer interfaces (ADR-0005 Phase 1 quick wins)

**What changes:** Move `Logger` and `DBer` interface definitions from component-internal packages to the `kernel` package as the canonical source. Update all component import paths.

**Security assessment:**

| # | Threat | Severity | Confidence | Notes |
|---|--------|----------|------------|-------|
| 1 | **Interface contract breakage** — if the hoisted interface differs from the original, components that implement it silently diverge | NONE | — | Mechanical refactor — the interface definitions are moved verbatim with no semantic changes. Go compiler catches any type mismatch at build time (compile-time safety). |
| 2 | **Import shadowing** — a component re-defines Logger/DBer locally after the hoist, creating two parallel types | LOW | 3 suppressed | Go's type system treats two identically-shaped interfaces from different packages as distinct types. **Verdict:** No security impact. Compile-time safety eliminates all plausible attack vectors.

### Change 2: Add `kernel/scope.go` with `WithProjectID` + `ProjectIDFromContext`

**What changes:** Introduces a typed context key (`projectIDKeyType`), exporter `WithProjectID(ctx, int64)`, and extractor `ProjectIDFromContext(ctx) (int64, bool)` in the `kernel` package.

**Existing pattern:** The codebase already uses `contextKey`-typed context values for `org_id`, `user_id`, `user_email`, and `user_role` — but these are duplicated across `components/auth/auth.go` and `components/api/api.go`. This story creates the canonical source at the kernel level.

```go
// New: kernel/scope.go
type projectIDKeyType string
const projectIDKey projectIDKeyType = "project_id"

func WithProjectID(ctx context.Context, projectID int64) context.Context {
    return context.WithValue(ctx, projectIDKey, projectID)
}

func ProjectIDFromContext(ctx context.Context) (int64, bool) {
    id, ok := ctx.Value(projectIDKey).(int64)
    return id, ok
}
```

**Security assessment:**

| # | Threat | Severity | Confidence | Notes |
|---|--------|----------|------------|-------|
| 1 | **Context key spoofing** — an external package injects `context.WithValue(ctx, "project_id", 42)` to impersonate a project | NONE (blocked) | 10 | The context key is typed (`projectIDKeyType`) and **unexported** (lowercase `projectIDKey`). External packages cannot construct a value of type `projectIDKeyType` because only the kernel package knows the type. `context.WithValue` matches keys using `==` on the interface type + value, so an identically-named string key in a different package is a different key. This is the Go standard pattern for preventing context key spoofing. |
| 2 | **Key collision with existing `contextKey("project_id")`** — if another package defines a different `contextKey` type with string value `"project_id"`, could cause unexpected behavior | LOW | 6 suppressed | Go context keys are matched by type+value. A `contextKey("project_id")` from package A is a different key than `projectIDKeyType("project_id")` from the kernel package. They are distinct types. The only risk is if a developer reads `ProjectIDFromContext` assuming it extracts a value they set with their own key — but the Go type mismatch would return `(0, false)` rather than silently returning wrong data. Suppressed per confidence < 8. |
| 3 | **Integer overflow in project_id** — attacker passes `math.MaxInt64` or negative project IDs | LOW | 7 suppressed | The function signature is `WithProjectID(ctx, int64)` and produces `(int64, bool)` — no validation on the integer value itself. However, project IDs are generated by the database (auto-increment) and passed through auth token claims (JWT verification). The kernel helper is a pure data carrier with no business logic — validation at the injection point (auth middleware) is the correct architecture, not at the transport layer. Suppressed per confidence < 8. |
| 4 | **Untyped context extraction in downstream code** — a component developer extracts project ID with `ctx.Value("project_id")` instead of `ProjectIDFromContext`, bypassing the type guard | LOW (code quality) | 5 suppressed | This is a developer discipline concern, not a vulnerability. The typed key still prevents spoofing even when extracted via raw `ctx.Value` — the key comparison is still type-safe. The risk is that `ctx.Value(projectIDKey)` returns `nil` and the developer mishandles it, but the `(int64, bool)` return pattern prevents nil dereference. Excluded per false-positive rules (code quality, not security). |
| 5 | **Context key exposure via reflection or unsafe** — if kernel is imported by a malicious component that uses `reflect` or `unsafe` to enumerate type names | NONE | 2 suppressed | This requires a malicious component already running inside the process — at that point the attacker has full process control. The kernel package trusts the components it registers. Excluded per false-positive rule: attacker with in-process code execution is not a boundary. |

**Verdict:** The typed, unexported context key pattern is the Go standard for preventing context key spoofing. This story is a **security improvement** — it creates a canonical source for project ID context injection that:
1. **Prevents spoofing** via unexported typed keys
2. **Prevents nil dereference** via `(int64, bool)` return  
3. **Eliminates duplication** of the ad-hoc `contextKey` pattern currently scattered across `api` and `auth` packages

## Mitigation Guidance

### During Implementation
1. **Verify unexported key:** Confirm `projectIDKey` (lowercase) in `kernel/scope.go` — this is the critical security property. If exported (`ProjectIDKey`), any package could inject spoofed project IDs.
2. **Type isolation:** Do not reuse `contextKey` from `auth` or `api` packages. The `projectIDKeyType` must be a distinct type definition.
3. **No default value:** `ProjectIDFromContext` must return `(0, false)` — not `(0, true)` — when no project ID is set. A default of `0` with `true` would bypass downstream `if !ok { return error }` checks.

### Future Dependents (e57s02–e57s05)
4. **Auth middleware injection (e57s04):** When auth sets `WithProjectID` from JWT claims, validate that `claims.ProjectID > 0` before injecting. A zero-value project ID injected via `WithProjectID(ctx, 0)` would satisfy `ProjectIDFromContext` (returning `0, true`), allowing a project-less token to pass downstream scope checks.
5. **DB query scoping (e57s03):** Downstream handlers must enforce `WHERE project_id = ?` on all queries when `ProjectIDFromContext` returns `ok == true`. The kernel helper is a transport mechanism — not an enforcement mechanism.
6. **Cross-project access defense (e57s04):** Auth tokens carry a single project ID. If multi-project access is ever added, the context key pattern must support a set of project IDs, not a single value — a protocol-level concern to revisit.
